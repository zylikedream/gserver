# 架构不变量

本文件是本仓库**唯一有约束力的架构约束清单**。ADR 记录"当时为什么这么定"（历史，只增不改）；本文件记录"现在什么必须成立"（当前状态，每次变更重写，不追加）。

**目标是一屏读完。** 超出即说明约束面失控，应先合并或删除条目，而不是继续追加。

## 需求与承载

本文件列的是**需求**；满足它的具体做法是**承载**，记在另一列。

三条规则：

1. **承载不约束需求。** 需要改动需求才能保住某个做法时，先怀疑那个做法——它多半是为旧实现长的。
2. **需求先重述，再实现。** 换基础组件时，先只确认新组件提供哪些保证，不解决"旧做法还能不能留"；之后逐个问：沿用、换做法、还是这个需求已不需要。
3. **需求集合本身可重估。** 需求随基础组件改变，不默认全部延续。

判断某条东西是需求还是承载，看**来源**：

> 它当初是为了迁就旧实现才长成这样的吗？

是 → 承载。

## 前提事实（非约束力）

设计假设成立所依赖的**外部事实**，不是规则。失效则重估相关不变量，而非继续沿用其承载。

- **A 同一节点名至多一个活进程**（编排约束）。换用自定义 registrar 后运行时不再替我们拒绝重名——默认 registrar 才返回 `ErrTaken`。失效 → 重估 #5、#6。
- **B 编排器会重启启动失败的实例**（k8s 默认 `restartPolicy: Always`，仓库未覆盖）。这是 #6 以「获取失败即启动失败」为承载的前提。失效 → 重估 #6。

## 效力规则

1. **只有本文件与状态为 `Accepted` 的 ADR 有约束力。** `Proposed` ADR、设计/实测文档、机制描述、参考实现、被拒方案——**零约束力**，只能作为理由。
2. **判据**：这句话被推翻会导致状态损坏吗？会 → 不变量；不会 → 理由。
3. **ADR 只写思考过程，不写实现。** 不写代码、函数、字段、配置键、行数。具体实现会失效；写进 ADR 后会以"像约束"的形态长期滞留。
4. **ADR 必须精简**，一个 ADR 只记一个决策。多个决策合并会使"改一处"被迫重开全部。
5. **新 ADR 必须在正文点名它触碰的不变量编号。** 保留/取代的映射集中在本文档的「状态 / 去向」列，不在 ADR 内重复。只列关联 ADR 不等于做过检查。
6. **审查与讨论只引用本文件或代码。** ADR 正文不作为论据——引用前必须对该条对代码重验一遍。
7. **需求 / 承载的判断由设计者决定。** 审查方只提供来源事实（它当初是否为了迁就旧实现才长成现在这样），不代为分类、不据此改文档。
8. **审查只提「不处理会导致状态损坏」且「实际可达」的问题。** 三个条件同时成立才值得提出：已验证（对代码或源码核过）、后果是状态损坏（而非某次操作失败）、现实路径可达（而非理论可达）。
   - 理论可达但代价可接受的情形：**不提出、不记录、不讨论**。已接受的风险不写进文档。
   - 已被否决或已决定搁置的议题**不得重复提出**。
   - 判断"是否值得提"的责任在审查方；把可接受的情形推给设计者判断，本身就是错误。
