# ADR 0008: Actor 运行时替换

- 日期：2026-09-16（2026-09-18 接受，拆分并精简；2026-09-19 据实测修正「门面变薄」这一预期，并修正推翻条件的判据）
- 状态：**Accepted**
- 关联：ADR 0006、ADR 0009–0014
- 原文档的其余决策已拆分：0009 跨节点编码、0010 身份与租约、0011 服务发现、0012 激活与所有权、0013 失败语义与可观测性

## 背景

底层 actor 运行时已停止维护，继续依赖意味着无人修复的缺陷与无人应答的兼容性问题。这是迁移的唯一驱动因素。

迁移对象是**运行时**，不是应用架构。现有装配根、模块生命周期、服务注册等结构本身没有暴露问题，因此不在替换范围内。

耦合面集中在 actor 门面：门面长期自行补齐了生命周期分发、请求应答、进程句柄、参数传递、追踪注入、日志适配、监督决策、激活协调等运行时本可提供的能力。

## 决策

换用仍在维护的运行时；门面重写，装配与生命周期模型保持原样。

- **保留**装配根、模块与生命周期、服务注册、定时调度语义。
- **不引入**新运行时的 Application/应用组合概念：它与现有模块职责重叠，引入会得到双份生命周期与两套失败语义。
- 门面必须保持为**深模块**：所有权、激活、跨节点编码的复杂度留在门面内，业务侧只看到少数入口，不得演化为对新运行时方法的一层浅转发。

本 ADR 触碰 `invariants.md` **#10（停机顺序）**：替换运行时即替换了 actor 的停止方式，因此必须
（a）使用等待终止回调完成的优雅停止，不得使用强制停止；
（b）保持共享客户端（数据库、缓存）晚于 actor 运行时关闭。
两者缺失任一，每次停机都会静默丢失最后一次存盘。

## 考虑过的方案

**自行 fork 维护旧运行时**：该运行时已无上游，自持意味着长期承担安全更新与语言版本兼容；换用仍在维护的运行时的成本可控且一次性，因此拒绝。

**引入新运行时的应用组合概念**：会与既有模块树形成双重生命周期与双份失败域，拒绝。

## 后果

- 原先手写的、运行时已提供的能力被删除，而非改写（会合机制、定时调度、进程句柄等）。
- **门面总量未降反升（实测）**。被删除的手写能力，由三项"旧运行时白送、新运行时不白送"的能力抵消：跨节点消息编码（新运行时的序列化不接受生成类型）、按节点名的服务发现适配、两种寻址模式（本机进程标识与跨节点注册名）。因此**"以删除为主"成立，"门面变薄"不成立**——后者原是基于"运行时已提供"的推测，实测表明该推测只对了一部分。
- 业务侧对运行时的依赖点随门面收敛，但**并非消除**：业务仍直接使用运行时的行为基类，回调签名中也有运行时类型（见 ADR 0014）。本条原是按"保留业务侧接口 + 适配层"的形态写的预期，形态改变后不再成立。
- 迁移期**不能新旧混跑**：两者传输层协议不同，必须停服切换。

## 推翻条件

- 目标运行时停止维护，或出现需要 fork 才能修的关键缺陷；
- 发现旧运行时具备而新运行时无法覆盖的既有能力；
- 迁移后门面中**手写补齐运行时能力**的代码不降反升，说明"以删除为主"的判断不成立。（判据是手写能力的方向，不是门面总行数——总行数受运行时是否附带某项能力影响。）
