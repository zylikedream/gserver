# ADR 0009: 跨节点消息编码

- 日期：2026-09-16（2026-09-18 接受，拆分并精简）
- 状态：**Accepted**
- 关联：ADR 0008

## 背景

新运行时的跨节点传输需要自行决定消息如何编码。可选路线有两条：为每种业务消息实现运行时原生序列化接口，或用一层统一信封承载已序列化的业务载荷。

项目已有完整的 protobuf 协议与消息注册表，业务消息本就是 protobuf。

## 决策

采用**单一信封**：信封带一个消息标识与已序列化的业务载荷；消息标识复用仓库已有的协议注册信息。只有跨节点投递才封装，本机投递保持零拷贝。

本 ADR 不触碰 `invariants.md` 中的条目。

## 理由

- 需要向运行时注册的类型从"全部业务消息"降为"一个信封类型"，注册面最小。
- 无生成代码，业务侧发送/接收签名不变。
- 代价是一个与消息大小无关的固定字节开销；在项目消息尺寸分布下占比很小。

## 考虑过的方案

**为每种 protobuf 类型实现运行时原生序列化**：需要为全部消息类型生成大量适配代码并逐个注册，而相比信封只省下很小的固定开销。收益与生成量不成比例，拒绝。

**直接向运行时注册 protobuf 生成类型**：该运行时的序列化会对生成类型中的私有字段报错，此路线不可行。

## 后果

- 信封的固定开销是所有跨节点消息的常数成本。
- 放弃运行时的类型级特性（握手期类型压缩、按类型的编解码统计）。若日后确有需求，可按类型分派与信封并存，不冲突。

## 推翻条件

- 实测表明该固定开销在真实消息分布下显著（当前记录为小比例常数）；
- 出现需要运行时类型统计或压缩的明确运维需求；
- 协议注册表出现覆盖缺口。
