# ADR 0014: 业务 actor 的接入形态

- 日期：2026-09-18（2026-09-19 补记）
- 状态：**Superseded by ADR 0017**（本 ADR 的形态决策已被取代；本文保留为当时的思考过程，**不再有约束力**）
- 关联：ADR 0008、ADR 0012、ADR 0017

## 背景

门面重写时，业务 actor 接入新运行时有两种形态：

- 业务侧保留一个自有接口，门面提供适配层把运行时回调翻译成对该接口的调用；
- 业务结构体直接内嵌门面基类（该基类内嵌运行时的行为基类），业务覆写运行时回调时显式调用基类同名方法。

旧运行时下是前者：业务实现门面定义的接口，由门面的适配层把运行时回调转发过去。

## 决策

采用**后者**：业务结构体直接内嵌门面基类，不保留业务侧接口与适配层。

本 ADR 不触碰 `invariants.md` 中的条目：它决定的是接入形态，不是任何"被推翻会导致状态损坏"的需求。

## 理由

- 适配层不含行为，只把一次调用换成另一次调用；换来的成本是双份方法集——运行时每多一个可覆写回调，就要在接口、适配层、基类三处各写一遍。
- 业务真正需要门面补齐的是"运行时没给而项目需要"的东西（带日志与追踪上下文的 context、按消息类型的反射分派、定时器、所有权），这些由基类提供，与是否保留接口无关。
- 门面的深度由基类实际补齐的能力支撑，而不是由接口形状支撑。保留接口得到的"看起来业务不依赖运行时"是形式上的——运行时回调的语义仍要由业务理解。

## 考虑过的方案

**保留业务侧接口 + 适配层**：多一层不含行为的转发，且运行时回调集合一变就要三处同步；它带来的唯一好处是业务侧的 import 更干净，代价则是每次回调变化都要重复劳动。拒绝。

## 后果

- 业务侧直接依赖运行时类型：内嵌的行为基类，以及回调签名中的进程标识与请求引用。
- **与 ADR 0008「业务侧不再直接依赖运行时类型」相反**，该条据此修正——原表述是按"保留接口+适配层"的形态写的预期，形态改变后不再成立。
- 覆写回调时必须显式调用基类同名方法，且两类回调的顺序有语义：初始化段先调基类（先取得所有权），终止路径后调基类（先落盘、后释放）。
- 更换运行时会触及业务代码（业务内嵌了运行时的行为基类）。

## 推翻条件

- 需要在不触碰业务代码的前提下更换运行时——当前形态做不到，业务内嵌了运行时的行为基类；
- 运行时回调集合频繁变动，导致基类方法集与业务覆写点反复失配。
