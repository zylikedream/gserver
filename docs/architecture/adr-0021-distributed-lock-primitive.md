# ADR 0021: 分布式锁原语改用成熟库

- 日期：2026-10-15
- 状态：**Proposed（暂缓执行）** — 调研已完成并记录在此；执行留到与 plot 写路径裁决同一轮。**本文零约束力**（见 `invariants.md` 效力规则第 1 条）。
- 关联：ADR 0020（测试替身放在真实边界上）
- 触碰不变量：无。本文替换的是一个「承载」，而它对应的需求（地块操作需要互斥）尚未列入 `invariants.md`；不变量 1–10 中没有任何一条描述这条锁。

## 背景

地块操作（种植类操作与偷花）需要在若干地块上互斥。这个互斥当前由一个自研的 redis 锁组件提供，它的形态是「一次锁多把键 → 执行临界区 → 返回后释放」，全仓库只有一条使用路径（地块锁）。

现在要决定的是：这个原语继续自研，还是交给成熟库。

## 观察

- 自研实现与地块缓存、偷花功能在**同一个功能提交**里进来，没有任何选型记录可查。
- 它的多键获取是**逐个获取 + 失败回滚**，不是原子的。
- 它**不提供续期**：临界区耗时超过 TTL 时，锁在 redis 里自行过期，互斥静默失效——没有错误、没有日志。
- 进程崩溃（含强杀）后锁会滞留到 TTL 到期，因为释放只有「持有者主动释放」一条路。
- 「引依赖」这个理由在当时并不成立：引入它的那一刻，两种自带租约续期与失效自动释放的组件已经在依赖与部署里了。

## 成因

需要的功能面很窄（一次条件写入 + 一段释放脚本），而 redis 客户端与本地可跑的 redis 替身都已经就位。把它写出来比先调研省事，于是「自研」成了默认，而不是被评估后的结论。

真正的代价不是行数，是**决策没有留痕**：下一个读到它的人（或下一个工具）只能靠翻提交历史还原「为什么是自己写的」，于是同一个问题被反复重开。本文就是那次重开的结果。

## 决策方向

**锁原语改用成熟库，自研实现只保留「业务需要的那个形态」这一层。** 本仓库不再自己维护条件写入脚本、令牌生成与重试退避。

选型按我们自己的需求排，不按通用排名：

1. **多键全或无**必须由服务端保证——这是使用路径唯一的形态差异点。
2. 释放必须校验持有者，不能释放别人的锁。
3. 兼容现有 redis 客户端（go-redis）。
4. **不新增基础设施**。
5. 现有 Go 版本可编译，且不因此被迫升级工具链。
6. 能在本地真实 redis 替身上跑同一条库路径，测试不需要为它留接缝。

选择：`github.com/bsm/redislock`。它是候选中唯一同时满足「服务端原子多键」与「零新增基础设施」的。

## 考虑过的方案

- **保持自研。** 拒绝。多键获取的非原子性是真实可达的（两个调用方反向获取同一组键），而这一条靠服务端一条原子命令即可消除；继续自研等于自己承担这块的正确性。
- **Redlock 类实现。** 拒绝。它的价值来自「多个独立 master 上的多数派容错」，单 redis 部署上付了全套机制却拿不到它的收益；且它没有多键原语，多键要自己拼排序与回滚——等于把本要删掉的代码重写一遍。
- **consul 会话锁。** 保留为备选。它是唯一自带周期续期、且会话失效即自动释放的方案，且 consul 已在部署里。代价：多键原子要自己拼，锁的可用性与 consul 可用性绑定，每次获取走一次一致性提交。
- **etcd 租约锁。** 拒绝。能力上最贴合（续期与 fencing 记号都是现成的），但部署模板里没有它——选它等于新增一套基础设施。
- **自研 + 看门狗。** 拒绝。续期只是问题的一半，另一半（多键原子）仍要自己扛；且这会把并发复杂度引回业务组件。

## 预期后果（尚未执行）

以下是本方向落地后应有的结果；文内所有结论均已对源码与实测核过（候选 API、版本约束、以及"多键原子获取 / 令牌校验释放 / 续期 / 丢锁可见"在本地 redis 替身上的行为）。

- 多键获取由服务端一次原子命令完成，不再依赖调用方先排序；「全程持有」由构造保证。
- 条件写入脚本、令牌生成、重试退避不再由本仓库维护。
- 丢锁从「完全不可见」变成可判别的错误值，可被日志与调用方区分。
- **它不提供续期看门狗**：续期能力有了，但仍需显式调用。因此「临界区超过 TTL」这个洞**依然存在**，只是现在有了低成本补法。
- **它不改变「锁说谎时靠谁兜底」**：锁在 TTL 内也可能失效（进程停顿长于 TTL 时，锁服务对此无能为力）。兜底只能来自写路径自身的裁决，那是另一个决策，本文不做。
