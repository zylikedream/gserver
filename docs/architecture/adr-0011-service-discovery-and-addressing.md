# ADR 0011: 服务发现与寻址

- 日期：2026-09-16（2026-09-18 接受，拆分并精简）
- 状态：**Accepted**
- 关联：ADR 0006、ADR 0008、ADR 0010

## 背景

系统里有两种寻址粒度，它们的需求不同：

- **actor 间寻址**：先到节点，再由节点按进程标识路由。节点级可达即可。
- **HTTP 端点寻址**：同一节点上并存多个服务且端口各异，必须按端点粒度解析。

新运行时的内置发现以**节点**为单位，无法表达端点粒度。

## 决策

三层职责分离（不变量 7），各自回答一个正交问题：

| 层 | 问题 | 载体 |
|---|---|---|
| 节点 → 地址 | 节点名如何解析为可达地址 | 运行时发现接口的自定义实现，读取**已有的**服务注册数据 |
| 能力 → 节点列表 | 哪些节点能承载某类 actor | 现有服务注册表与选择器（保留） |
| 实体 → 归属 | 某实体归哪个节点的哪个世代 | 租约 + 世代（ADR 0006，保留） |

配套决策：

- **不引入运行时的应用级发现**：其粒度为节点，地址还需二次解析，且项目必须为 HTTP 端点保留细粒度注册；actor 复用同一套机制，避免在注册中心并存两种记录类型。
- **不新增第二套注册记录**：全系统仍只有一个组件写注册中心。
- **不采用静态路由**：静态路由是每节点本地的且匹配后不再回退发现，横向扩容需要所有既有节点改配置。

## 理由

actor 的寻址是"节点 + 进程标识"，因此节点级发现足够；HTTP 端点是"节点 + 端口"，节点级发现不足。两者的差异决定了必须保留细粒度注册中心，而保留它之后，actor 再引入第二套节点级记录只会增加查询与一致性面。

## 考虑过的方案

**用运行时的应用级发现承载能力目录**：粒度为节点，且地址需另行解析，无法表达同节点多端口；同时会导致注册记录分裂。拒绝。

**用静态路由替代发现**：扩容需改全部节点配置，拒绝。

（不构成拒绝理由的两点：维护态标记可用运行时标签表达；按 key 哈希的放置策略可在调用侧自行实现。）

## 后果

- 注册中心保留，但只由一个组件写入。
- 运行时发现实现需要一个"从节点名解析到地址"的约定，其可行性依赖"节点名与能力名同名"这一配置约定（见下方待定）。
- 运行时发现实现必须显式提供连接所需的协议版本信息：与静态路由不同，解析接口返回的路由没有"缺省补全"这一步。

## 待定（无约束力）

- **actor 端口的分配方式与注册时序**：若由系统分配端口，需要保证注册记录中的端口与实际监听一致；该时序是发现层的前提，需先行验证。
- **一节点多能力的开发配置**：多能力共用一个节点时不满足"节点名与能力名同名"的约定，需定义退化行为或明确为开发环境限制。

## 推翻条件

- 解析接口无法在建立连接前取得正确的协议版本，导致连接失败；
- 端点粒度需求消失（HTTP 服务并入 actor 或交由编排器接管），则细粒度注册中心可整体退役。
