# ADR 0016: 运行时回调与业务入口分离

- 日期：2026-09-19
- 状态：**Accepted**
- 关联：ADR 0013、ADR 0015

## 背景

门面把运行时回调直接开放给业务覆写，业务按需覆写后再显式调用基类同名方法。这个约定对**所有**回调一视同仁，但回调的性质并不相同：

- 一部分回调里，基类做的是**机制**——把定时消息路由到已注册的回调、把跨节点消息还原信封。这些动作与业务无关，业务覆写时若不显式回调基类，机制就被静默关掉。
- 另一部分回调是**纯业务扩展点**，覆写即替换默认行为，不回调基类也无副作用。

两者混在同一个名字下，于是"覆写业务处理"与"保留机制"变成同一件事。实际后果已经出现：两个 actor 覆写了消息入口却未回调基类，它们注册的周期定时器从未触发——其中之一是空闲连接清理，另一个是周期存盘。两者都只在特定时长后显现，常规回归覆盖不到。

## 决策

**把运行时回调与业务入口分开，业务只覆写业务入口。**

- 运行时回调保留在门面层，负责机制：定时消息分流、跨节点消息还原、错误语义转换。**业务不覆写它们**，因此机制不可能被绕过。
- 业务消息入口是独立的名字，业务按需覆写，默认实现走分派。
- 这一分离对基类分层中的每一层都成立。
- **业务对象由运行时持有的行为实例取得**，不作为构造参数传入：运行时持有的就是工厂返回的最外层结构体，构造时把自身传一遍是多余的。

本 ADR 不触碰 `invariants.md` 中的条目：它决定的是门面与业务的接口划分，不改变任何"被推翻会导致状态损坏"的需求本身。

## 理由

**为什么不是"要求业务记得回调基类"**：约定依赖记忆，而违反约定的代价是静默的——没有编译错误、没有运行时告警，只是某些机制再也不执行。凡是"忘了就静默失效"的约定，都应该改成"想违反也做不到"。

**为什么机制必须由门面独占**：定时路由、信封还原这些动作的输入来自运行时，与业务语义无关。它们既然不由业务决定，就不应出现在业务的覆写点上——否则每个业务实现都在重新决定要不要保留它们。

## 考虑过的方案

**保留现状，仅在文档中强调"覆写时必须回调基类"**：约定已经存在，但缺陷仍然发生了两次。理由不成立的前提是人的记性可靠，而这不是可以依赖的东西。拒绝。

**在基类里检测业务是否调用了基类**（如标记位 + 告警）：把"静默失效"改成"告警失效"，仍要靠人看日志去发现问题，且检测本身需要额外状态。拒绝。

**让运行时机制不经消息入口，改由运行时直接回调**：定时消息由运行时投递到邮箱，必经消息入口；绕过邮箱就失去了"在 actor 上下文中串行执行"的保证。拒绝。

**构造时把业务对象自身作为参数传给基类**：能得到同样的转发能力，但每次构造都要传自己一遍，且简单到不需要业务入口的 actor 也被迫传一个用不上的值。运行时本来就持有最外层实例，无需业务再声明一次。拒绝。

## 后果

- 业务不可能通过覆写入口意外关闭门面机制，包括定时器路由与跨节点消息还原。
- 业务的消息入口换名，四个 actor 随之迁移。
- 门面多一层间接：运行时回调 → 业务入口 → 分派。
- 到达业务入口依赖一次**接口断言**（而非类型断言）：业务对象是内嵌基类的外层结构体，不是基类本身；内嵌提升的方法会进入它的方法集，接口断言查得到，类型断言查不到。这一区别在本仓库造成过一个静默失效——工厂里用类型断言写入能力名，断言永不成立，覆写从未发生（见 ADR 0015 后果）。

## 推翻条件

- 出现业务确实需要接管消息入口（如在还原信封之前介入）的场景，说明分离的位置不对；
- 业务入口的默认实现无法覆盖常见需求，导致每个 actor 都要重写一遍它。
