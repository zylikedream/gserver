# 测试用例规范

> 索引:AGENTS.md development tips
> 架构约束(`invariants.md`「测试替身规则」)不在此重复,只引用。
> 本文档是可操作约定:怎么写,不解释为什么。

## 一句话约定

**测试把实现锁死在契约上,是好事;锁死在形状上,是坏事。**

判据不是覆盖率。是这一句:

> 把被测生产代码改坏一行,这个测试会红吗?
> 举不出具体的改法 → 它不是测试,是注释。

## 一、重构安全(优先级高于其他所有)

重构时测试红了,默认动作不应该是改代码。按顺序问三句:

1. **这个测试的名字说的是契约还是实现?**
   名字里有方法名(`TestInit`、`TestGetMethods`、`TestTcpConnectorType`)→ 几乎必然是结构 → **改测试**。
2. **我能举出一个具体的、用户可见的故障吗?** 举不出来 → 改测试。
3. **只有前两问都过了,才改生产代码。**

### 硬规则

- **禁止为了让测试变绿而修改生产代码的行为**,除非能说出被破坏的具体 bug 场景。这是 review 时唯一需要拦的 diff 形态。
- **测试改动与生产改动在 PR 里必须可区分。** 混在一起就没有审查点。
- **重构 PR 里测试红了,优先怀疑测试** —— 重构的定义就是「行为不变」。行为真变了的话,那个改动不该以重构的名义提交。

### 结构性约束(写测试时就定,不是 review 时才看)

| 禁止 | 理由 | 反例 |
|---|---|---|
| 断言生产的**内部调用顺序** | 实现自由 | 断言假锁对象的 `order == [1,2,3]` —— 改批量获取/并发获取就红,但三个实现可能都满足防死锁 |
| **复制生产代码的逻辑**再断言 | 两份会分叉,两边都失去意义 | 手抄一份 `reflect.SelectCase` 断言长度 |
| 持有生产的**字段布局** | 等于把结构变成契约 | 测试里直接改 actor 的字段 |
| 断言**完整 SQL 字符串** | 改个别名就红 | 改表别名、字段顺序即失败 |

**唯一例外**:顺序本身就是被保护的不变量(锁序、fence 锁必须在写入之前)。那就写断言,但必须在注释里写明「顺序本身是被保护的契约」并说明后果。

「严格 mock 是结构敏感噩梦」是这条的通用表述:替身越精确,测试越绑死实现。

## 二、只写这四类

对着 `invariants.md` 的三条件(已验证 / 后果是状态损坏 / 现实可达)过一遍,三条同时成立才写:

| # | 类别 | 判据 | 本仓库实例 |
|---|---|---|---|
| 1 | **不变量** | 跨调用恒成立的状态约束,违反 = 静默状态损坏 | fence 锁序;steal;friend 的 `lockBoth` 升序 |
| 2 | **边界与状态转换** | 阈值、配额、状态机合法/非法迁移 | 令牌桶补充 vs Burst 封顶;公会权限矩阵;半包 |
| 3 | **裁决与优先级** | 多个来源冲突时谁赢 | 限流 Ack 码;mod 分发优先级 |
| 4 | **边界上的拒绝** | 非法输入必须被拒,且**错误语义/错误码**正确 | 哨兵注册;handler 权限拒绝分支 |

第 4 类常被漏。负例测试的密度要够 —— 它们和正例一样是契约。

## 三、明确不写这四类

1. **语言与框架本身** —— Go 的 map、`encoding/json`、`gjson`、`gconv`。
2. **编译期已经保证的事** —— 类型、`iota` 常量顺序、常量真值。
3. **转发与接线** —— mock 回声、构造函数入参回读(`service.host` 恒等于传入值)、返回自己返回的常量。
4. **生产逻辑的手抄副本** —— 见第一节。

## 四、每个测试必须能回答的三问

| 问 | 不合格的样子 |
|---|---|
| ① 它防什么 bug? | 「三种类型都出现过」—— 99.9% 恒返回同一个值的实现能过 |
| ② 生产改一行能让它红吗? | 断言对两种实现都成立(断言本身分辨不出差异) |
| ③ 它红了能直接告诉我是哪里坏了吗? | 只断 `err == nil` —— 分不清是依赖连不上还是被测逻辑坏了 |


## 四之二、注释(强制)

**每个测试函数都要有 doc comment,写清楚「测什么」和「为什么需要」。** 不是建议,是准入条件 —— 没注释的测试视为未写完。

### 两行内容,缺一不可

```go
// TestWithSortsAndReleases:With 必须按字典序加锁,并在回调执行期间同时持有全部锁。
// 为什么:乱序或依次释放的加锁起不到防死锁作用,两个反向的双边操作会互相持有对方需要的行锁。
func TestWithSortsAndReleases(t *testing.T) {
```

- **第一行「测什么」**:写契约,不是写方法名。`TestX_Init` → 「无法解析的频道 id 必须被拒绝,而不是生成 kind/id 全零的坏 actor 投进集群」。
- **第二行「为什么需要」**:写出**后果**。不是复述断言,是回答「不这样会怎样」。写不出第二行的,先想清楚这个测试到底为什么存在 —— 想不出来就该删。

### 最该注释的三类

1. **差异藏在 setup 里的** —— 同一个名字、同一句断言、不同的注入点。读者无从区分,必须注释。
   *例*:三个租约围栏测试的差异分别是 token 不匹配 / 续约报错 / 续约被阻塞,断言长得几乎一样。
2. **断言有上下文的** —— 时延上界、容差、「这一步证明什么」被下一步盖住的。
   *例*:20ms 是上界不是精度要求;令牌桶的前半步证明补充、后半步证明封顶。
3. **fixture 模拟了生产哪一处** —— 标注 `生产 xxx.go:75`,这样生产改动时知道该动哪。

### 文件级 doc comment

每个测试文件开头写三件事:验证什么规则 / 规则来源 / 未来谁违反时这个测试会红。

```go
// Package errortest 验证错误处理规范(cockroachdb/errors)的硬性规则。
//
// 规则来源: docs/development/error-handling.md
// 本测试用实验事实固化规范, 未来有人违反规范(如用 fmt.Errorf %w 包装
// cockroachdb 错误、对已有栈的错误 WithStack), 此测试即失败。
```

范本:`tests/error/error_semantics_test.go`。

### 注释写不出来的信号

**写不出「为什么需要」→ 这个测试可能不该存在。** 这是删除判据,不是补注释的理由。硬凑的注释比没有更坏:它会让人以为有人想过。

## 五、命名

**注释见上节(强制)。此处只讲名字。**

- **名字写契约,不写方法名。** ❌ `TestChannelActor_Init_InvalidFormat` —— 复述方法,读者看不出「不能解析的频道 id 必须被拒绝,而不是生成 kind/id 全零的坏 actor 投进集群」。
- **名字必须和实际走到的路径一致。** 名字叫 A 路径、实际走 B 路径,比没测试更坏 —— 它让人以为 A 被覆盖了。用一个早退分支绕开真正的路径,是最常见的形态。
- **三个及以上近似用例合成一张表**,表上按上节写两行注释。

## 六、替身与 seam

架构约束见 `invariants.md`「测试替身规则」。此处是它对**测试侧**的反向含义:

- **依赖只从三处进入**:显式参数、构造注入的字段、真实边界替身。替身替换的是**对端**(DB / Redis / 另一个服务 / actor),不是被测的那个函数。
- **替身越精确,测试越绑死实现。** 精确 SQL + 精确调用序列的 mock 是最强的结构敏感来源。优先断言可观察的副作用,而不是内部调用轨迹。
- **helper 不得在 SUT 初始化之后再覆盖 SUT 解析出来的状态。** 否则后续所有断言反映的是注入的常量,不是 SUT 的行为。
- **seam 的价值是双向的**:它让现在能测,也让以后改这个函数不用改那一处。**一个让重构变贵的测试,是它建错了 seam 的信号** —— 该改的是 seam 的设计,不是删测试。
- **外部依赖必须 gate。** 需要真实 Consul / Redis / DB 的测试必须调对应的 `requireXxxIntegration(t)`;否则默认跑就是顺序/环境炸弹。
- **测试必须自带清理,顺序无关。** 包级 `testCfgInited` 这类 guard 必须有重置路径,且每个 flag 都有。不对称的重置(一个能重置、另一个不能)必然产生顺序依赖。

## 七、删除压力

**删除标准比新增标准更严。** 没有任何测试能作为「存在理由」时,直接删,不要「改一改留下」—— 除非它能通过第四节三问。

**删完重复测试后如果该包出现覆盖空洞,要显式记录,不要静静删掉。** 空洞是信息,掩盖它才是损失。

## 八、反例词典

| 症状 | 一句话 |
|---|---|
| 只有日志 / 没有断言 | 删 |
| 断言自己的构造,不碰生产代码 | 删 |
| 断言编译期保证 | 删 |
| 手抄生产逻辑 | 删 |
| 名字与实际路径不符 | 改测试(优先级高于「补断言」) |
| 无 doc comment | 补(强制,不通过即视为未写完) |
| 只有注释没有断言 | 删 |
| 断言分辨不出实现差异 | 补断言 |
| N 个近似用例 | 合表 |
| 测试依赖外部环境未 gate | 加 gate |
| 缺意图注释 | 补注释,写理由 |

## Review 检查清单

- [ ] 这个测试红了,是契约被破坏,还是实现被换了形状?
- [ ] **每个测试都有 doc comment?写清了「测什么」和「为什么需要」两件事?**
- [ ] 名字说的是契约还是方法?
- [ ] 名字和实际走到的路径一致吗?
- [ ] 断言对两种不同的实现会给出不同结果吗?
- [ ] 它依赖内部调用顺序 / 字段布局 / 完整 SQL 吗?(顺序若是受保护不变量,注释写了没有)
- [ ] 有没有抄生产代码?
- [ ] 有没有断言其实走不到的路径?
- [ ] 外部依赖 gate 了?清理了自己的状态?
- [ ] 意图注释写的是理由还是名字的复述?
- [ ] 文件级 doc comment 写了规则来源?

## 风格范本

- `tests/error/error_semantics_test.go` —— 文件级 doc comment(规则来源 + 违反时测试即失败)、表驱动、断言计数和不变量而非 golden 字符串
- `core/gxynet/processor/processor_test.go:40-43` —— fixture 注释标注 `生产 ltiv.go:75/86`
- `src/apps/role/internal/logic/role_rejection_test.go` —— 「声明即入册」的表 + 反向测试(证明服务端故障绝不降级)
- `src/apps/role/internal/logic/actor_response_test.go:8-10` —— 注释直接写出后果:「载荷不是期望类型时必须返回错误, 而不是让调用方在断言上 panic——一次断言失败会让整个 role actor 终止、玩家掉线」
- `src/apps/gateway/internal/logic/login_limiter_test.go:20-21` —— 文件级注释写清取舍:「测试不替换内部时钟或定时器, 一律调配置 + 等真实条件成立」
